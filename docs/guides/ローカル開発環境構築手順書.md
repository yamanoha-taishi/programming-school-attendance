## 3. Laravel + Inertia + React プロジェクト作成（`web`フォルダに直接作成）

`laravel new` は対話形式でstarter kitを選ばせるインストーラーです。ローカルにPHP/Composerを入れずに済むよう、Composerの公式Dockerイメージを使って一時的にインストーラーを実行します。

`web` フォルダはまだ存在しないため、`laravel new web` として直接作成できます（`docs/` `memo/` と衝突しません）。

```powershell
cd C:\GitHub\programming-school-attendance

docker run --rm -it -v "${PWD}:/work" -w /work composer:2 `
  bash -c "composer global require laravel/installer && /tmp/vendor/bin/laravel new web"
```

このコマンドは、Composerの公式イメージを一時的なコンテナとして起動し、その中で①`laravel/installer`をグローバルインストールし、②生成された`laravel`コマンドをフルパス（`/tmp/vendor/bin/laravel`）で直接呼び出して`web`フォルダにプロジェクトを作成しています。フルパスで呼び出しているのは、このComposerイメージが`COMPOSER_HOME`を`/tmp`に設定しているため、インストールされたコマンドの実体が`/tmp/vendor/bin/laravel`になるためです。

※「`In NewCommand.php line 1443: Application already exists!`」というエラーが出た場合は、`web`フォルダが（中身が空でも）すでに存在していることが原因です。Laravelのインストーラーは、対象フォルダが1つでも存在すると、中身の有無に関わらずこのエラーで止まる仕様になっています。`dir C:\GitHub\programming-school-attendance\web`で中身を確認し、重要なファイルが無ければ`Remove-Item -Recurse -Force C:\GitHub\programming-school-attendance\web`で削除してから、コマンドを再実行してください。

対話プロンプトが出たら、以下のように選択します（`laravel/installer` v5.31.1で確認済み。バージョンによって質問内容が変わることがあります）。

- Do you want to use a starter kit? → **Yes**
- Which frontend stack should your starter kit use? → **React**
- Which authentication provider do you prefer? → **Laravel's built-in authentication**（WorkOSは外部SSO認証サービスで別途アカウントが必要。今回は会員番号＋パスワードの自前認証をPhase 2で組み立てるため、標準の認証機能をベースにする）
- Would you like to add teams support to your application? → **No**（複数人でチームを作って切り替えるSaaS的な機能。今回のアプリに「チーム」という概念はないため不要）

テストフレームワークは自動的にPHPUnitになり、DBは一旦SQLite（`web/.env`の`DB_CONNECTION=sqlite`）で初期化されます。これは後述のStep4-5で、Docker＋PostgreSQL用の設定に上書きします。

完了すると、`C:\GitHub\programming-school-attendance\web\` にLaravelプロジェクト一式が生成されます。

※最後に `The command "'npm' 'install'" failed. ... sh: exec: line 0: npm: not found` というエラーが表示されますが、無視して大丈夫です。インストーラーが最後の仕上げとして自動で`npm install`を実行しようとしますが、この`composer:2`イメージにはNode.js／npmが入っていないため失敗します。これは想定通りで、npmのインストールは次のStep4で`node`コンテナの中で行うため、ここで失敗しても後工程でカバーされます。Laravel本体（`vendor/`フォルダやmigrationなど）は正常に作成済みです。

## 4. Docker環境構築（`web`フォルダ配下に作成）

`web` フォルダ直下に、以下のファイルを作成します。

### 4-1. `web/docker/php/Dockerfile`

```dockerfile
FROM php:8.4-fpm

RUN apt-get update && apt-get install -y \
    git unzip libpq-dev libzip-dev \
    && docker-php-ext-install pdo pdo_pgsql zip

COPY --from=composer:2 /usr/bin/composer /usr/bin/composer

WORKDIR /var/www/html
```

※ベースイメージを`php:8.4-fpm`にしているのは、Step3で`composer:2`イメージ（内部的にPHP 8.4系を使用）を使って`composer.lock`を生成しているため。ここを`php:8.3-fpm`のような古いバージョンにすると、後述の`composer install`実行時に「`laravel/framework`や`symfony/*`パッケージが`php >=8.4.1`を要求しているのに、コンテナ側は8.3系」という不整合で失敗します（`composer.lock`が確定させたバージョンと、実行環境のPHPバージョンを一致させる必要があるため）。

### 4-2. `web/docker/node/Dockerfile`

```dockerfile
FROM node:22-alpine

RUN apk add --no-cache php84 php84-openssl php84-mbstring php84-tokenizer php84-xml php84-fileinfo php84-dom php84-pdo php84-curl php84-session \
    && ln -sf /usr/bin/php84 /usr/bin/php

WORKDIR /var/www/html
```

`node`コンテナは本来Vite開発サーバー専用ですが、これとは別に最小限のPHP CLIも入れています。理由は、starter kitに標準で入っている`@laravel/vite-plugin-wayfinder`というViteプラグインが、開発サーバー起動時に自動で`php artisan wayfinder:generate --with-form`というLaravelコマンドを実行し、ルート定義からTypeScript用の型定義ファイル（`resources/js/routes`・`resources/js/actions`）を生成する仕組みになっているためです。この処理は`node`コンテナの中でその場で実行されるので、`node`コンテナ自身にPHPが無いと失敗します（`app`コンテナにPHPがあっても別コンテナなので届きません）。

インストールしている拡張の`php84-session`は特に必須です。これが無いと、Laravelのセッション処理が要求する`SessionHandlerInterface`が見つからず、`Interface "SessionHandlerInterface" not found`というエラーで`wayfinder:generate`が失敗します（Alpineの`php84`パッケージは、標準構成に`session`拡張を含まないため）。

### 4-3. `web/docker/nginx/default.conf`

```nginx
server {
    listen 80;
    index index.php index.html;
    root /var/www/html/public;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass app:9000;
        fastcgi_index index.php;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }
}
```

### 4-4. `web/docker-compose.yml`

```yaml
services:
  app:
    build:
      context: .
      dockerfile: docker/php/Dockerfile
    volumes:
      - .:/var/www/html
    depends_on:
      - db
    environment:
      DB_CONNECTION: pgsql
      DB_HOST: db
      DB_PORT: 5432
      DB_DATABASE: ${DB_DATABASE}
      DB_USERNAME: ${DB_USERNAME}
      DB_PASSWORD: ${DB_PASSWORD}

  web:
    image: nginx:alpine
    ports:
      - "8000:80"
    volumes:
      - .:/var/www/html
      - ./docker/nginx/default.conf:/etc/nginx/conf.d/default.conf
    depends_on:
      - app

  node:
    build:
      context: .
      dockerfile: docker/node/Dockerfile
    working_dir: /var/www/html
    volumes:
      - .:/var/www/html
    ports:
      - "5173:5173"
    command: sh -c "npm install && npm run dev -- --host"

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: ${DB_DATABASE}
      POSTGRES_USER: ${DB_USERNAME}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - db-data:/var/lib/postgresql/data
    ports:
      - "5432:5432"

volumes:
  db-data:
```

`docker-compose.yml`はこの後 `web` フォルダの直下から実行する前提なので、`.`は`web/`自身を指します（`docs/` `memo/`はビルドコンテキストに含まれません）。`node`サービスは、公式の`node:22-alpine`イメージをそのまま使うのではなく、4-2で作った独自Dockerfileから`build`する形にしています。

役割の整理：

- **app**：PHP-FPMだけを動かす（HTTPは受けない）
- **web（サービス名）**：nginxが80番でリクエストを受け、`.php`はappにfastcgiで渡す（フォルダ名の`web`とはたまたま同じ名前になっていますが別物です。紛らわしければサービス名は`nginx`に変えても構いません）
- **node**：Vite開発サーバー（HMR用）。本番ビルドとは別枠。前述の理由でPHP CLIも同居させている
- **db**：PostgreSQL本体

### 4-5. `web/.env` の調整

APP_URL=http://localhost:8000

### 4-7. 起動と初期化

```powershell
cd C:\GitHub\programming-school-attendance\web

docker compose up -d --build

docker compose exec app chmod -R 777 storage bootstrap/cache
docker compose exec app composer install
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate
```

各コマンドの意味：

- `chmod -R 777 storage bootstrap/cache` … `storage/`（ビューキャッシュ・ログなど）と`bootstrap/cache/`は、Laravel実行中に書き込みが必要なフォルダです。これらはStep3でComposerの一時コンテナ（root権限）が作成したファイルですが、実際にPHPを動かす`app`コンテナのPHP-FPMワーカーは`www-data`という別ユーザーで動いているため、そのままでは書き込み権限がありません。権限を緩めて誰でも書き込めるようにしています（ローカル開発環境なので問題ありません。本番環境では別の方法をとります）。これをやらないと、ページを開いたときに`tempnam(): file created in the system's temporary directory`というエラーになります。
- `composer install` … PHPの依存パッケージをインストールし、`vendor/`フォルダを生成します
- `key:generate` … アプリケーションの暗号化キー（`APP_KEY`）を生成します
- `migrate` … `users` `sessions` `cache` `jobs`など、starter kit標準のテーブルをDBに作成します。これを実行しないうちにブラウザでアクセスすると、セッション管理用の`sessions`テーブルが無いため「`relation "sessions" does not exist`」というエラーになります（テーブル定義書を元にした本来のmigrationは、この後のPhase 1で作成します。ここではDB接続確認を兼ねています）

`http://localhost:8000` にアクセスして、Laravel + Inertia + Reactの初期画面が表示されれば成功です。

※途中で`app`や`node`だけを個別に再ビルドした場合（例：Dockerfile修正後に`docker compose up -d --build`を再実行したときなど）、`web`（nginx）コンテナだけが起動しっぱなしで残っていると、「`502 Bad Gateway`」が出ることがあります。nginxは起動時に`app`のIPアドレスを名前解決してそれを覚えたまま動き続けるため、`app`コンテナが新しく作り直されてIPアドレスが変わると、古いIPアドレス宛てにリクエストを送ってしまい接続できなくなるためです。この場合は`docker compose restart web`でnginxを再起動すると解消します。

## 6. GitHub Actions雛形（lintのみ）

リポジトリ直下（`web/`ではなく`C:\GitHub\programming-school-attendance/.github/workflows/lint.yml`）に作成します。ロードマップの通り、この段階ではlintのみで、テスト・デプロイはPhase 5以降で追加します。

```yaml
name: Lint

on:
  push:
    branches: [main]
    paths: ["web/**"]
  pull_request:
    paths: ["web/**"]

jobs:
  php-lint:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: web
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: "8.4"
      - run: composer install --no-interaction --prefer-dist
      - run: vendor/bin/pint --test

  js-lint:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: web
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "22"
      - run: npm ci
      - run: npm run lint:check
```

補足：

- `working-directory: web` … リポジトリ直下ではなく`web/`フォルダの中でコマンドを実行する指定
- `paths: ["web/**"]` … `docs/`や`memo/`だけを変更したコミットではlintが走らないようにする指定（なくても動作に支障はないが、無駄な実行を減らせる）
- `vendor/bin/pint --test` … Laravel標準のコードスタイルチェッカー（Laravel Pint）。`--test`は「修正はせず、問題があれば検出するだけ」のオプションです
- `npm run lint:check` … starter kitの`package.json`には、自動修正する`lint`（`eslint . --fix`）と、チェックのみ行う`lint:check`（`eslint .`）の2つが用意されています。CIでは「問題があれば検出して落とす」のが目的なので、修正を試みない`lint:check`の方を使います

コミット・pushして、GitHubのActionsタブでワークフローが動くことを確認したらPhase 0は完了です。

```powershell
git add .github/workflows/lint.yml
git commit -m "GitHub Actionsのlintワークフローを追加"
git push
```
