# 実装ロードマップ

- 作成日：2026-08-13
- 更新日：2026-08-17

設計フェーズ（要件定義書・テーブル定義書・画面一覧・遷移図・WF）が完了したことを受けて、実装フェーズの進め方を整理する。要件定義書7章の開発優先順位（運営向けスマホ→保護者向けスマホ→運営向けPC→保護者向けPC）に沿って組み立てている。

## Phase 0：開発環境構築

- Laravel（バックエンド）＋Inertia.js＋React（フロントエンド）構成のプロジェクト作成
- Docker（docker-compose）でのローカル開発環境構築
- GitHubリポジトリ作成、初期コミット
- GitHub Actionsの雛形作成（この段階ではlintのみでも可。テスト・デプロイは後続フェーズで追加）

## Phase 1：DB実装

- テーブル定義書を元にmigrationを作成（students／guardians／staff／holidays／school_classes／lessons／lessonPlans／sections／attendances）
- マスタ系（sections／school_classes／lessons／lessonPlans／holidays）はSeederで登録（要件定義書8章：スコープ外・将来対応のマスタ管理画面を作らない前提のため）
- デモ用ダミーデータ（guardians／students／staff／attendances）をFactory＋Seederで用意。要件定義書6章の通り、実在の教室名・個人情報は使用しない

## Phase 2：認証実装

- 会員番号（member_code）＋パスワードでのログイン（入力された会員番号でguardians・staff両方を検索し、一致した方のテーブルで認証する。保護者は0001番台、スタッフは5001番台から採番しているが、これは見分けやすくするための採番範囲の分離であり、テーブル判定は先頭文字や番号の範囲ではなく検索結果のヒットで行う。詳細はテーブル定義書のstaffセクション参照）
- guardian／staffの2種類のLaravel guardを設定
- パスワードのハッシュ化、初期パスワード発行（保護者・スタッフとも登録時に発行）
- メール登録済みの場合のセルフサービスパスワード再設定（保護者・スタッフ共通の仕組み）

## Phase 3：運営向け画面実装（スマホ優先）

WFがある画面から、画面一覧・遷移図の遷移順に実装する。

1. ログイン画面（共通）
2. 出席記録・一覧画面
3. 管理メニュー画面
4. 保護者一覧画面／保護者登録・編集画面
5. 生徒一覧画面／生徒登録・編集画面
6. スタッフ一覧画面／スタッフ登録・編集画面
7. プロフィール設定画面（運営向け）

## Phase 4：保護者向け画面実装（スマホ優先）

1. 出席予定・履歴確認画面
2. 欠席・遅刻・補講登録画面
3. プロフィール設定画面（保護者向け）

## Phase 5：CI/CD拡充

- GitHub Actionsにテスト実行（PHPUnit／Pestなど）とビルドを追加
- mainブランチへのマージをトリガーにデプロイを実行する仕組みを検討

## Phase 6：デプロイ

- **本番環境：Render（Web Service、Dockerデプロイ）＋Neon（PostgreSQL、無料枠）の組み合わせを採用**（2026-08-14決定。Render単体の無料PostgreSQLは30日でデータごと自動削除される仕様のため、DBは期限のない無料枠を持つNeonを採用。Supabaseも候補だったが、Neonの方が素のPostgresに近くLaravelの公式ガイドもあり、余計な考慮〈publicスキーマの扱いなど〉が少ないため採用）
  - ローカルのdocker-compose構成（app／web／node／db）は、本番用に1コンテナへ統合したDockerfile（nginx＋PHP-FPM）へ作り替える（Render Web Serviceは1コンテナ・1ポートが基本のため）
  - dbコンテナの代わりに、Neonの接続情報（`DATABASE_URL`等）を環境変数で設定
  - Viteのビルド成果物（`npm run build`）をデプロイ時に生成し、node（Vite dev server）は本番では使用しない
  - `APP_KEY`はローカルで生成した値を固定して環境変数に設定（コンテナ再作成のたびに再生成しない）
  - デプロイ時に`php artisan migrate --force`などを自動実行する仕組みを用意
- 環境変数の設定、ダミーデータのシード投入
- 外部からアクセス可能な状態にする（要件定義書6章）

## Phase 7：PC対応・仕上げ

- 運営向けPCサイト → 保護者向けPCサイト（要件定義書7章の優先順位通り、スマホ実装が終わってから着手）
- README・プロジェクト概要ページの整備（採用担当者などポートフォリオを見る人向け）
- デモURL・スクリーンショット・工夫点のまとめ

## 未決事項（実装前に決めておきたいこと）

- **ビジュアルデザイン**：WFはあえてグレースケールのモックアップだったため、実装時の配色・タイポグラフィなどのデザインシステムを別途決める必要がある
- **API／ルーティング設計**：Inertia.jsの各ページに対応するLaravel側のルート・コントローラーの一覧化（画面一覧・遷移図を元に作成できる）
